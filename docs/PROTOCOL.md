# TodoDrop 传输协议 v2

手机端（待办投递 App）把选中的未完成待办按项目树发给 PC 端 CLI（命令 `tdd`），只传原始数据；
CLI 负责包装成 Markdown，每个顶层项目保存为一个 `TODOS_<项目名>_yyyyMMdd_HHmmss.md`。

> 版本说明：协议 v1 由手机生成 Markdown、CLI 原样保存为一个文件；v2 改为只传原始数据。
> 二维码格式没有变化（仍是 `tododrop://v1`），`GET /api/v1/info` 的路径也保持不变，
> 两端版本不一致时 App 会在探测阶段提示「版本不兼容」。

整体思路参考 LocalSend：HTTPS + 自签证书 + 证书指纹校验。区别在于：

| LocalSend | TodoDrop |
|---|---|
| UDP 组播发现设备 | PC 终端显示二维码，手机扫码获得地址 |
| 接收方弹窗确认 | 扫码即授权（二维码里带一次性 token） |
| prepare-upload + upload 两步 | 单个 `POST /api/v2/todos` |

## 1. 二维码内容

二维码是一个 URL：

```
tododrop://v1?h=<ip1>,<ip2>&p=<port>&t=<token>&f=<fingerprint>&n=<name>
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `h` | 是 | PC 的候选 IPv4 地址，逗号分隔，1–4 个，按优先级排序 |
| `p` | 是 | HTTPS 端口（1–65535），默认 53320 |
| `t` | 是 | 本次运行的访问 token：16 字节随机数，base64url 无填充（22 个字符） |
| `f` | 是 | 服务器证书（DER 编码）的 SHA-256，base64url 无填充（43 个字符，解码后 32 字节） |
| `n` | 否 | PC 显示名，URL 编码，最长 32 个字符 |

- scheme 固定为 `tododrop`，host 部分固定为 `v1`（协议版本）。
- 未知参数必须忽略，便于以后扩展。
- token 和证书在 CLI 每次启动时重新生成，CLI 运行期间一直有效。

## 2. 传输层

- HTTPS（TLS 1.2 / 1.3），证书为 CLI 启动时生成的自签 ECDSA P-256 证书。
- 客户端**不做**常规的 CA 链和主机名校验，而是计算服务器叶子证书 DER 的 SHA-256，
  与二维码里的 `f` 做常量时间比较，不一致则中止握手。
- 客户端并发连接 `h` 中的所有地址，以第一个 `GET /api/v1/info` 成功的地址为准，然后取消其余连接。

## 3. 鉴权

所有请求都必须带：

```
Authorization: Bearer <token>
```

token 缺失或不匹配返回 `401`。服务器用常量时间比较 token。

## 4. 接口

所有响应体都是 `application/json; charset=utf-8`。出错时响应体为 `{"error": "<中文错误信息>"}`。

### 4.1 `GET /api/v1/info`

探测用，确认地址可达、token 正确，并比对 `protocol`。这个接口的路径和字段在各版本之间保持不变。

```json
{"app": "tododrop", "protocol": 2, "name": "DESKTOP-X", "version": "0.2.0"}
```

### 4.2 `POST /api/v2/todos`

请求头 `Content-Type: application/json`，请求体：

```json
{
  "protocol": 2,
  "device": "Xiaomi 14",
  "exportedAt": "2026-11-19T15:30:45+08:00",
  "projects": [
    {
      "name": "工作",
      "todos": ["写周报", "修复登录页崩溃\n第二行正文缩进续写"],
      "notes": ["周五前交"],
      "children": [
        {"name": "后端", "todos": ["接口文档"], "children": [{"name": "数据库", "todos": ["加索引"]}]}
      ]
    },
    {"name": "生活", "todos": ["买牛奶"]}
  ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `protocol` | 是 | 固定为 `2` |
| `projects` | 是 | 顶层项目列表，每个顶层项目在电脑上生成一个文件 |
| `device` | 否 | 手机名称，只用于 PC 端日志 |
| `exportedAt` | 否 | 手机端导出时间（ISO 8601），只用于日志 |

项目节点：

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 项目名 |
| `todos` | 否 | 待办原文（可以多行），按 App 里的顺序，默认空 |
| `notes` | 否 | 只给人看的「提醒」原文，**不写进文件**，只在 PC 终端里显示，默认空 |
| `children` | 否 | 子项目，结构相同，默认空 |

- 项目最多 3 层（顶层算第 1 层），超过返回 `400`。
- 手机端只发子树里有选中待办的项目；这些项目会带上自己的全部提醒。空列表字段可以省略。
- 未知字段必须忽略。

成功返回 `201`，`files` 的顺序和请求里顶层项目的顺序一致（没有有效待办的顶层项目不生成文件，也不出现在这里）：

```json
{
  "files": [
    {"project": "工作", "savedAs": "TODOS_工作_20261119_153045.md", "count": 4},
    {"project": "生活", "savedAs": "TODOS_生活_20261119_153045.md", "count": 1}
  ],
  "notes": 1
}
```

| 字段 | 说明 |
|---|---|
| `files[].project` | 顶层项目名（规范化成单行后的） |
| `files[].savedAs` | 电脑上保存的文件名 |
| `files[].count` | 写进这个文件的待办条数 |
| `notes` | 收到的提醒条数 |

| 状态码 | 含义 |
|---|---|
| `201` | 已保存 |
| `400` | 请求体不是合法 JSON、`protocol` 不是 2、字段类型不对、层级超过 3 层，或者没有任何有效待办 |
| `401` | token 缺失或错误 |
| `413` | 请求体超过 2 MiB |
| `500` | PC 端写文件失败，`error` 中带原因；这一批里已经写好的文件会被删掉 |

## 5. 保存规则（PC 端）

- 每个顶层项目一个文件：`TODOS_<项目名>_yyyyMMdd_HHmmss.md`，时间取 PC **收到时**的本地时间。
- 文件名里的项目名：`<>:"/\|?*` 和控制字符换成 `_`，连续空白合并成一个空格，去掉首尾的空格和点，最长 40 个字符；为空时用「未命名」。
- 同名文件已存在时依次尝试 `..._2.md`、`_3.md`……不会覆盖已有文件（两个同名的顶层项目也靠这个区分）。
- 一次请求的多个文件要么全部保存，要么一个都不留。
- 内容按 UTF-8 写入（无 BOM，换行符为 `\n`）。
- 保存目录优先级：`-o` 参数 > 配置文件 `default_dir` > 当前工作目录；目录不存在时自动创建。
- 提醒不写进文件，在终端里用醒目的颜色列出，带上所在项目的路径。

## 6. Markdown 格式（PC 端生成）

顶层项目自己的待办是开头的平铺 GFM 任务列表（不写顶层项目名，项目名已经在文件名里），子项目、孙项目分别用 `##`、`###` 标题分节：

```markdown
- [ ] 写周报
- [ ] 修复登录页崩溃
  第二行正文缩进续写

## 后端

- [ ] 接口文档

### 数据库

- [ ] 加索引
```

- 顺序：和请求里的顺序一致（即 App 里看到的顺序）；同一个项目里先写自己的待办，再写子项目。
- 正文统一换行符为 `\n` 并去掉首尾空白；第二行起每行缩进 2 个空格、去掉行尾空白；空行丢弃；正文全是空白的待办跳过。
- 子项目和它的子项目里都没有有效待办时，不写这个子项目的标题。
- 标题里的项目名规范化成单行（换行换成空格）。
- 小节之间空一行，文件以 `\n` 结尾。
